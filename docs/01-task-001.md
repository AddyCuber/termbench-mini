# 01 — Task 001 (nginx static site)

## What this is

A task is a broken Linux machine plus a hidden pass/fail check. Task 001 is the pipeline smoke test: nginx should serve two static pages on port 8080, but three independent bugs keep it down. The agent (later) only sees `task.yaml`'s prompt. `tests/` and `solution/` never go into the Docker image.

## How data flows

1. `environment/` is the **only** Docker build context. The image has nginx, curl, procps, a broken `site.conf`, and pages under `/srv/site`. Nginx is not started.
2. `scripts/manual_check.sh 001` builds that image, starts a container with `sleep infinity`, `--network none`, 1 CPU and 1g RAM, and no host mounts.
3. It `docker cp`s `tests/` in and runs `test.sh`. That must fail (nginx is down / config is invalid).
4. It `docker cp`s `solution/solve.sh` in and runs it. The reference fix repairs the listen semicolon, the document root, and `index.html` permissions, then starts nginx.
5. Tests run again and must pass: process up, `nginx -t` ok, `/` and `/about.html` return 200 with the original text, a missing path returns 404, and sha256 of both files matches the originals.
6. The container is removed on exit (success or failure).

The verifier checks **outcomes**, not which commands were run. Forbidden prompt substrings (`semicolon`, `chmod`, `permission`) are for the later validator so the prompt does not spell the fix.

## Three questions you should be able to answer

1. Why is `environment/` the only build context, and how do tests still run?
2. Why does a 404 for `/does-not-exist` plus sha256 of the page files belong in `test.sh`?
3. What are the three bugs, and why is it fine if a strong model always solves this task?
